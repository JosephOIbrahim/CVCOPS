## 1. Thesis

**Copernicus is the brush and OpenCV is the eye.** Copernicus synthesises and filters on the GPU, and Houdini 22 ships no node that measures motion in footage. OpenCV measures motion well, but it cannot share GPU memory with Houdini.

So OpenCV works at the edge of the graph, on small analysis images, and Copernicus does everything else. The first release is one optical-flow node built that way.

The long game reverses the roles. OpenCV becomes the test bench, and native OpenCL kernels found by search do the work inside Copernicus. Section 7 shows how to get there without betting on it.

## 3. The one judgment call

**Is the GPU the goal, or the means?** v1 made CUDA execution a requirement. This version treats the GPU as a means and ships the capability first.

| Option | What it costs | What you get |
| --- | --- | --- |
| Capability first (my pick) | Five missions and no compiler | A working flow node on a stock wheel, then GPU work where a measurement earns it |
| GPU engineering first | A custom OpenCV 5.1 CUDA build on Windows before the first pixel | The GPU story early, on a backend tied to one vendor |

The choice turns on what you want from the project, not on performance data. If the GPU work itself is what you want to build or show, say so and Mission 6 moves to the front.

My view goes one step further. The GPU path worth owning is native OpenCL inside Copernicus, which runs on any GPU Houdini supports, not a CUDA worker beside it.

## 4. First principles

Nine rules drive every decision below. When a later section looks arbitrary, one of these is the reason.

1. **Cross the boundary once, with the smallest payload.** Python cannot reach Houdini's GPU buffers, and Copernicus has no HDK. Every hop is GPU to host to file and back, so prepare and post-process in native COPs and send one small grey image per frame.
2. **OpenCV is the eye; Copernicus is the brush.** OpenCV is used only for analysis Copernicus lacks. Anything Copernicus already filters on the GPU stays native.
3. **Operations are pure functions.** Arrays and parameters go in; arrays and a receipt come out. The library never imports `hou`, so every operation is testable anywhere.
4. **The agent can only verify what it can run.** Every mission ends in one command that passes or fails. There are three rungs: pure tests anywhere, `hython` on the workstation, GPU on the 4090.
5. **If you can score it, you can search it.** A pass or fail check lets an agent finish. A numeric score lets a search improve. Evolution is allowed where a trustworthy score exists, and nowhere else.
6. **Nothing is silent.** The backend is explicit, recorded and never substituted. A missing cache is an error on the node, and a stale one is a warning.
7. **Use Houdini's machinery before writing ours.** ROP Image Output writes and File COP reads. There is no job queue and no socket protocol.
8. **Build beside upstream.** Their repo stays pinned and untouched. Fixes travel as pull requests.
9. **Earn every optimisation.** A faster path must cut end-to-end median time by 20% on a named workload. If the operation is under a quarter of the job, stop: no backend can get there.

## 5. Architecture

**Each frame crosses the boundary once, as a small file.** Houdini prepares and exports a grey analysis image, one worker process estimates the flow, and Houdini loads the result and converts it in a single node.

1. **Prep, in native COPs.** Luminance, gain, gamma and an optional downscale produce one grey analysis layer.
2. **Export, by ROP Image Output.** It writes `analysis.####.exr`, raw, plus one extra frame so every baked frame has a successor.
3. **Estimate, in the worker.** `python -m cvcops flow` reads frames N and N+1, runs the recipe, and writes `flow.####.exr` with its receipt.
4. **Import, by File COP.** It loads the flow as raw RGB. A missing frame is an error.
5. **Convert, in one node.** It applies analysis scale, axis sign and units, and outputs `flow` and `valid`.

Three lanes share that contract, and only the first is in v0.1.

| Lane | What runs where | Status |
| --- | --- | --- |
| Bake | The five steps above, with one subprocess per bake | v0.1 |
| Live | A Python Snippet COP calls the same recipe in-process on every cook | Gated on probe P5 |
| GPU | Same contract; OpenCL through `cv2.UMat` first, a CUDA build second | Gated on measurements |

The worker has its own environment: a `uv`-managed CPython 3.13 with `opencv-python-headless==5.0.0.93`, `numpy` and `OpenEXR`. Houdini's own Python is never modified.

EXR is the exchange format because Houdini reads and writes it natively and float32 keeps sub-pixel precision. Receipts are JSON files beside the frames, so nothing depends on EXR header metadata.

## 6. Flow contract v1

**Treat flow like a motion-vector AOV: comp never asks which renderer wrote it, only whether channels, units and space match.** The comparison breaks in one place. A renderer's vectors are ground truth from geometry, and optical flow is an estimate, so this file carries a validity channel.

| Item | Contract | Status |
| --- | --- | --- |
| Analysis image | 8-bit, one channel, same size for A and B. Luminance weights, gain, gamma and analysis scale are recorded. | Verified: DIS rejects anything else |
| Exchange in | `analysis.####.exr`, raw, written by ROP Image Output. The worker quantises to 8-bit. | Probe P3 |
| Direction | Forward, A to B: the content at pixel p in A is at p + flow(p) in B. | Verified by fixture |
| Stored convention | `opencv_px`: x right, y down, pixels of the analysis image, per frame pair. The worker never converts. | Verified |
| Conversion | Exactly one node in the asset applies scale, sign and units. A known-motion fixture tests it. | Probe P4 |
| Exchange out | `flow.####.exr`, float32 RGB: R is u, G is v, B is validity, 1 or 0. A backward-flow file is written when validity is on. | Round trip verified bit-exact |
| Validity | Forward-backward agreement under a recorded tolerance, an in-bounds destination, and the optional input mask. It is a flag, not a confidence. | Design |
| Time | Frames A and B, fps and interval are recorded. There are no temporal hints, so results never depend on cook order. | Design |
| Resolution | Mismatched sizes are rejected. Nothing resizes implicitly. | Design |
| Recipe | A named pure function `estimate_flow(a, b)`. Stock presets are recipes too. The receipt records its name and source hash. | Design |
| Determinism | Same inputs, parameters and build give identical bytes on CPU. | Verified on 5.0.0 |
| Receipt | `flow.####.json`, written last through a temp file and an atomic rename: status, input digests, parameter digest, recipe, `cv2` version and build hash, backend, timings. | Design |
| Cache key | Input digests, parameter digest, recipe hash and backend. The asset shows fresh, stale or missing. | Design |
| Limits | Patch size stays at or below 16 before OpenCV 5.1, which fixes a heap overflow above that. The OpenCL path is only eligible at patch size 8. | From the 5.1 source and commit log |

## 7. Evolve lane

**OpenEvolve fits exactly one part of this project today: the flow recipe.** [OpenEvolve](https://github.com/codelion/openevolve) mutates a marked region of a program with an LLM and keeps what an evaluator scores higher. It needs four things: a program to edit, a numeric score, cheap evaluations and a budget.

| Target | Score | Cost per evaluation | Verdict |
| --- | --- | --- | --- |
| Flow recipe `estimate_flow(a, b)` | Speedup behind an accuracy gate against exact ground truth | About a second, CPU only, no Houdini | First target |
| Validity rule | Agreement with ground-truth occlusion masks | About a second | Second, same harness |
| Native OpenCL kernels | Speedup behind an exact-match gate | Seconds, and a headless GPU harness | Later, for a kernel the receipts show is hot |
| Prep constants: gain, gamma, scale | Numeric tuning only | Trivial | No. Use a sweep |
| Assets, node UX, looks | None that can be trusted | Minutes | No |
| This blueprint | Only an LLM judge's opinion | Not applicable | Not with the tool. Gated review passes instead |

I built the evaluator before recommending the lane. It follows OpenEvolve's own [background-blur example](https://github.com/codelion/openevolve/tree/main/examples/background_blur): quality is a hard gate and speed is the score.

| Check | Result in the sandbox, OpenCV 5.0.0, 960 by 540 |
| --- | --- |
| Runs under OpenEvolve 0.4.1 | The config loads and the cascade evaluator runs. No model calls were made. |
| Six deliberate cheats | All score 0, each with a stated reason. |
| Honest recipes on the dev suite | Half-resolution MEDIUM scores 3.6 to 3.9 times. Stock FAST scores 4.4 to 4.7 times. |
| My first gate | Wrong. Absolute thresholds rejected the reference itself on unseen fixtures. The gate is now relative to the reference on each fixture. |
| Five unseen fixture seeds | Stock FAST fails all five. My half-resolution recipe fails three. Only MEDIUM passes. |
| Two improvements written by intuition | Both lost to the seed. |
| Not done | No evolution run. The sandbox had no model for it to call. |

So the open question for the search is concrete. Is there a recipe at least 15% faster than MEDIUM that holds the gate on five unseen seeds? If 300 iterations find none, MEDIUM already sits on the front, and that is worth knowing.

Eight rules govern the lane.

1. **The evaluator is the product.** Write the cheats first and prove they score zero before spending a token.
2. **Gates are hard and relative to a reference.** Fast and wrong scores zero. Each fixture is judged against the reference's own error on it.
3. **Grade the worst region, not the average.** A mean hides an erased object. The worst 32 by 32 block does not.
4. **Time fairly.** One evaluation at a time, reference and candidate interleaved, a warm-up, the minimum of several runs, an idle machine.
5. **The search never touches its judge.** Only the marked block in one file may change. The evaluator, the fixtures and the contract are fixed.
6. **The holdout decides.** A candidate is promoted only if it passes every unseen seed and beats the best passing stock preset by 15%.
7. **Evolved code enters like any other code.** A reviewed change, rung-1 tests green, recipe name and hash in the receipt.
8. **Budget first.** A local model behind an OpenAI-compatible endpoint is the default. Claude through the Claude Code CLI is a one-block swap with a per-call cap. Start with 100 iterations and read the trace after the first 20 to 50.

**The north star is OpenCV as oracle and OpenCL as runtime.** Once the lane has promoted one recipe, the same evaluator can score native OpenCL kernels, with OpenCV and ground truth as the judge. Flow would then run inside Copernicus, live, on any GPU Houdini supports. This is a hypothesis with one unanswered probe, so it stays parked.

## 9. Operating rules for Claude Code

**Rules that cannot bend are enforced by the harness, and the rest live in a short CLAUDE.md.** This follows Anthropic's own [guidance](https://code.claude.com/docs/en/best-practices): CLAUDE.md is advice, while hooks and deny rules are enforcement.

| Rule | Enforced by | Why |
| --- | --- | --- |
| Rung-1 tests pass before a turn ends | A Stop hook running `tools/check.py`, where exit code 2 blocks | "Looks done" is not done |
| `vendor/` is read-only | A deny rule on edits under `vendor/` | Upstream is not ours to change |
| No `hou` import under `src/` | A unit test that scans imports | Keeps operations testable anywhere |
| No install into Houdini's Python, and no Houdini GUI | CLAUDE.md | Protects the install; an agent cannot judge a viewport |
| One mission per session, then `/clear` | CLAUDE.md | A focused context is cheaper and sharper |
| Evidence with every "done" | CLAUDE.md | The command and the tail of its output go into `docs/STATE.md` |
| No fan-out | CLAUDE.md | One optional read-only reviewer pass per mission, against this blueprint, skipping style |
| Model tiers are one line | CLAUDE.md | Heavy is your default model and Light is a cheaper one. Swap by editing the line. |
| Runtime beats documentation | Probes, then `docs/FACTS.md` | Houdini's docs leave conventions open |

Mission 0 writes the hook and the deny rule once the check script exists. In hook mode the script prints failures to stderr and exits with code 2. Confirm both with `/hooks` and `/permissions` afterwards.

```json
{
  "permissions": {
    "deny": ["Edit(./vendor/**)"],
    "ask": ["Bash(git push *)"]
  },
  "hooks": {
    "Stop": [
      { "hooks": [ { "type": "command", "command": "uv run python tools/check.py --hook" } ] }
    ]
  }
}
```

Only missions that rung 1 can fully verify may run unattended: M1, M2, MU and ME. Give each a turn or budget cap.

## 10. Upstream track

**Five fixes and one request go to MotionCOPs as pull requests, not into a fork.** Each fix arrives as a failing test plus a patch. The author must rebuild the affected assets, because a pull request cannot carry a reviewable binary.

| Finding | Where | Fix | Test |
| --- | --- | --- | --- |
| Integer luminance loses its scale | `_layer_values`, lines 161 to 195 of the recorder script | Normalise integer samples before the weighted sum | Fixed8 and Fixed16 white read 1.0 in both modes |
| The final fractional sample has no index | `_frame_index`, lines 283 to 292 | Search the actual sample list with a tolerance | Schedule (1, 2, 0.3) maps to indices 0 to 4 |
| Bookkeeping precedes publication | `_append_slice`, lines 584 to 621 | Update `captured`, `last_frame` and the range only after the cooks succeed | A forced failure leaves the state unchanged |
| Pixel sort write conflict | The `pixel_sort` kernel in the Pixel Sorting 1.1 asset | Gather form: each pixel reads its pair and writes only itself | Every pass is a permutation of the row, checked against a CPU model |

| No licence | Repo root | Ask the author to add one | |

Houdini 22 now ships native Time Shift, Time Blend, Time Pack, Time Loop and a Ripple solver. MotionCOPs' own Time Shift, Frame Blend and Ripple tools predate them. That is worth an issue upstream and no work here.

## 11. Risks and kill criteria

**Each risk has a signal to watch and a response decided in advance.**

| Risk | Signal | Response |
| --- | --- | --- |
| Orientation, sign or colour is wrong at the Houdini boundary | The M3 fixture fails | Fix it in the one conversion node. Fall back to `.npy` plus a Python import only if EXR cannot be made raw. |
| File I/O dominates the bake | Receipt timings | Batch frames per process, test EXR compression, lower the analysis scale. Do not reach for CUDA. |
| The CUDA build becomes a time sink | More than one session | Stop and keep CPU and OpenCL. The NVIDIA flow SDK is single-vendor and dormant. |
| `cv2.UMat` is silently CPU | UMat timing equals CPU timing | Label the backend best-effort. Only `cv2.cuda` is provably GPU. |
| Upstream stays unlicensed | No reply | Ship none of their files. Examples ask users to install MotionCOPs themselves. |
| The OpenCV 5.1 wheel changes results | Thresholds fail after the upgrade | Receipts carry the version, so caches invalidate by key. Re-qualify before adopting. |
| The search overfits its fixtures | A candidate passes the dev suite and fails the holdout | That is the holdout working. Never promote on the dev score. |
| No evolved recipe beats stock | 300 iterations without a promotion | Stop. Keep the stock presets and record the result. |
| Scope creep | A fourth node before v0.1 ships | Park it in section 12. |
| Indie-built assets may downgrade commercial sessions | Probe P7 | Ship the builder script, so each user builds under their own licence. This one is unverified. |

## 12. Parked until v0.1 ships

**Nothing below starts before the release gate.** The operations are ranked by value for motion design and by the size of the gap in native Copernicus.

1. Motion matte: MOG2 or KNN background subtraction from locked-off footage.
2. Feature tracks: KLT points with ids, delivered to SOPs.
3. Stabilise and match: multi-scale ECC to transform parameters.
4. Superpixel and segment stylisation from contrib `ximgproc`.
5. Neural flow through the native ONNX Inference COP, behind the same contract and without OpenCV.
6. Native OpenCL flow kernels, the north star in section 7.

Do not build an HDK plug-in, zero-copy OpenCL or CUDA sharing, a job queue, a socket protocol, or any node Houdini 22 already ships. That list includes corner detection, blobs to points, depth through MoGe-2, masks through SAM2, denoise and FFT.
