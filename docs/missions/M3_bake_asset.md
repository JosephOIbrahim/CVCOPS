# Mission M3: the bake asset

A proposal from the planning panel of 2026-11-10, not adopted. The blueprint's M3 row governs; this brief adds the
order, the files and the checks. Graph and conventions: `docs/missions/GRAPH.md`.

**Goal.** Build the flow asset by script from `houdini/build/controls.json`. It exports the analysis image, runs the
worker once per bake, loads the flow and converts it in one node. One example scene, whose bake receipt records
medians over five runs.

**Entry.** M2 is closed and committed. The committed `tests/thresholds/mission.txt` lists M3. If not, write
`WAITING:` and stop.

**Done when.** `uv run python tools/check.py --houdini` passes both M3 rows (two regions at analysis scale 1.0 within
0.10 px, and at 0.5 within 0.25 px). `docs/facts/m3_bake_receipt.json` holds medians over five runs for export, flow
compute, worker I/O and load; `tests/unit/test_bake_receipt.py` checks it at rung 1, because `check.py --houdini`
does not read that file. Joe has confirmed the arrows. `docs/STATE.md` holds the closing commands, their tails and the
DEC input line. (Under GPU first, the blueprint also asks for a bake with the provisional CUDA recipe. STATE records
the means, not the goal, as the default, so this brief leaves that out.)

**Tier.** Heavy. Not unattended: the arrows and the labels need Joe, and every rung-2 run holds his only licence.

## How the sessions run

Planned as two sessions (OD-17). The reason goes into STATE before the first build: the harness proves several parts
per hython call, and each call starts a licence.

**Session 1: probes, network, asset, bake.**

1. **Read** `CLAUDE.md`, `docs/BLUEPRINT.md`, `docs/FACTS.md`, `docs/STATE.md`, `docs/CONTROLS.md` and this brief.
2. **Baseline.** Rung 1 passes for M0 to M3. Rung 2 exits 1 with exactly two M3 rows failing on "not built yet".
   Record the hython path from `local.toml` with its size and sha256. Exit 3, or a licence error, means `BLOCKED:`
   and no code edit (OD-19).
3. **Pause.** `WAITING:` with the plan, the controls table generated from `controls.json`, the new-file list and the
   M3 questions. In the same sitting Joe confirms labels and defaults, picks the Frame Range default, and writes the
   package file into his own Houdini (or chooses MPlay). Stop.
4. **Probe first.** One hython run answers the kernel, token, export, isolation and asset questions. Any conditional
   ask it trips goes to Joe before the node that needs it.
5. **Build the network one node at a time**, each proved by a part of `probes/m3_network.py`: ports, prep, downscale,
   export, then import and convert.
6. **Build the asset and self-test it** from a fresh hython, through the judge's package and through `package.py`'s
   own file. A load that needs installFile is `BLOCKED:`.
7. **Bake.** The lane's three rung-1 nodes (glue, sidecar, aggregator) are copied back by now. With `bake.py` in, the
   stamped tree has changed, so rebuild the asset and re-run the self-test once. Then bake smoke,
   `bake_once.py --mode flow`, and the first values run of both rows, all on that build.

**Session 2: example, timing, Joe, close.**

8. **Example.** Frames, scene, bake, render and, with Joe's go-ahead, the saved scene.
9. **Time on an idle machine.** Run 1 alone; then five runs, each in the foreground or with the turn held open on
   Monitor. No lane, subagent or other check runs.
10. **Audit** the example's receipts.
11. **Arrows.** Joe opens the scene (or the EXRs in MPlay) and closes Houdini after. The reviewer pass runs meanwhile.
12. **Close.** Self-test on the final build, rung 1, rung 2, the values run, the hython identity, STATE with the DEC
    input line. Joe commits.
